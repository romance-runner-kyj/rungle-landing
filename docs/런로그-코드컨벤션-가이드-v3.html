0핵심 원칙 — 규칙이 사는 곳 3계층

컨벤션 내용보다 먼저, 각 규칙이 어디에 살지부터 정합니다. AI가 코드 대부분을 쓰는 팀에서 이 결정이 가장 큰 레버리지입니다.

2CLAUDE.md 작동 원리 (2026-07 기준)

규칙을 어디에 둘지 정하려면 로딩·우선순위·최신 기능을 알아야 합니다.

2-1. 로딩과 우선순위

  • CLAUDE.md는 매 세션 시작 시 전부(길이 무관) 로드되며, system prompt가 아니라 그 뒤의 user message로 주입됩니다 → 준수는 권고. 반드시 일어나야 하는 일은 Hook으로.
  • 실효 우선순위: 시스템 프롬프트(내장 기본 동작) → CLAUDE.md(권고) → 실시간 채팅 지시. 채팅 지시가 CLAUDE.md를 이깁니다.
  • 파일 계층은 덮어쓰기가 아니라 이어붙임(concatenate). 좁은 범위가 나중에 로드되어 충돌 시 우선.
  • 하위 디렉토리의 CLAUDE.md는 그 디렉토리 파일을 읽을 때 on-demand 로드 — 우리처럼 ios/·backend/를 나누는 모노레포에 정확히 맞는 메커니즘. 서버 작업 중 Swift 규칙이 컨텍스트를 차지하지 않습니다.
  • <!-- --> HTML 주석은 주입 전 제거 → 사람용 메모를 토큰 비용 없이 남길 수 있음.
  • @path/to/file import 지원(최대 4 hops). 단 import해도 컨텍스트 절약은 안 됩니다 — 시작 시 전부 로드. 절약이 목적이면 아래 2-3.

2-2. 파일 계층 — 우리 팀 기준

파일공유용도

2-3. .claude/rules/ — path-scoped rules

YAML frontmatter로 paths: glob을 지정하면 그 경로의 파일을 만질 때만 규칙이 로드됩니다. 평소 토큰 비용 0. "CLAUDE.md는 짧게, 세부는 rules로"를 가능하게 하는 도구입니다. 예시는 템플릿 D.

2-4. 유지 규칙 — Two-Strikes Rule

  • 규칙 추가 시점(공식): 같은 실수 2회째 / 리뷰가 "Claude가 알았어야 할 것"을 잡았을 때 / 지난 세션 교정을 또 칠 때. 1회면 아직 추가하지 않습니다.
  • 규칙이 있는데 계속 어긴다 → 파일이 너무 길다는 신호 → 가지치기하거나 Hook/린트로 승격.
  • 정말 중요한 몇 줄엔 IMPORTANT/YOU MUST — 단 전부 강조하면 아무것도 강조 안 됨. "be careful" 같은 약한 표현 대신 강한 명령형.
  • 월 1회, 코드처럼 리뷰·리팩터링. 변경은 반드시 PR로 — 규칙도 코드입니다.

4iOS 컨벤션 Swift · SwiftUI

iOS 17+ 전제의 단일 규칙. 도구가 강제할 수 있는 것은 도구 설정으로 밀어내고, 여기엔 판단이 필요한 것만 남깁니다.

4-1. 네이밍 AI가 가장 크게 반응

  • 타입/프로토콜 UpperCamelCase, 그 외 lowerCamelCase. Swift는 상수에도 SCREAMING_CASE를 쓰지 않음 → let maxPaceThreshold = 12.0
  • Boolean은 단언으로: isUploading, hasGPSFix, canShare
  • 단위를 이름에: distanceMeters, durationSec — API 계약(6번)과 동일 표기
  • 사용 지점의 명확성 > 간결성. 인자 라벨로 문장처럼: match(media: assets, to: session)
  • 파일 1개 = public 타입 1개, 파일명 = 타입명. 도메인 타입은 합의된 용어만: RunSession, MediaAsset, CandidateScore, ReelTemplate, Draft…

4-2. 포매팅 — 전부 도구로 CLAUDE.md에 적지 말 것

SwiftFormat(자동 포맷) + SwiftLint(관례·스멜). 설정 파일을 커밋하고 Hook·CI에 연결하면 이 카테고리의 논쟁은 소멸합니다. 4 스페이스·줄 120자·import 정렬 같은 값 자체는 .swiftformat·.swiftlint.yml에만 존재합니다.

🚫 error로 처리 (크래시 주범)force_unwrapping · force_cast · force_try — 프로덕션 코드에서 !·as!·try! 금지. 테스트 코드는 예외 허용.

4-4. SwiftUI 상태 관리 — @Observable이 기본

한 줄 규칙 모델/VM은 @Observable 매크로. 생성하는 뷰는 @State, 전달받는 뷰는 일반 프로퍼티(양방향 필요 시 @Bindable). ObservableObject/@Published/@StateObject는 신규 코드에서 금지 — 옛 예제 복붙으로 섞여 들어오는 걸 막는 규칙입니다. 
@Observable @MainActor
final class BestCutViewModel {
    private(set) var candidates: [CandidateScore] = []
    private(set) var isAnalyzing = false

    private let apiClient: RunLogAPIClientProtocol   // 프로토콜 주입

    init(apiClient: RunLogAPIClientProtocol) { self.apiClient = apiClient }
}

struct BestCutView: View {
    @State private var viewModel: BestCutViewModel   // 이 뷰가 생성·소유
    var body: some View { ... }
}
  • body는 선언만 — 50~70줄 넘으면 별도 View struct로 추출(@ViewBuilder 프로퍼티 말고)
  • 비동기 로딩은 init이 아니라 .task { await viewModel.load() } — 뷰가 사라지면 자동 취소
  • 순수 표시용 화면엔 VM을 강제하지 않음 — 로직/서비스 호출이 있는 화면만 VM

4-5. 동시성

  • 신규 코드는 async/await만. completion handler 스타일 API(PhotoKit 일부 등)는 Services 래퍼 안에서 withCheckedThrowingContinuation으로 변환해 가둠
  • UI 상태를 갱신하는 ViewModel은 클래스 전체 @MainActor
  • 미디어 수집·업로드는 구조적 동시성(TaskGroup)으로 병렬화 — 단 업로드 동시성 한도(예: 3)를 상수로 명시
  • Swift 6 strict concurrency는 결정 ⑨

4-6. 에러 처리 AI 최대 위험 지점

🚫 절대 금지 빈 catch {} · 버리기용 try? · "로그 찍고 계속". 에이전트는 코드를 "돌아가게" 하려고 에러를 조용히 삼키는 경향이 가장 강합니다. 처리하거나 전파하고, 증상이 아니라 근본 원인을 고칩니다.
  • 도메인별 타입 에러: enum UploadError: Error, enum SelectionError: Error — 사용자에게 보여줄 메시지와 분리
  • 권한 거부(HealthKit·사진)와 오프라인은 에러가 아니라 정상 상태 — 안내 UI·재시도 큐로 연결, 크래시·무한 스피너 금지
  • 서버 에러는 API 계약(6-4)의 errorCode로 분기 — HTTP 상태코드 매직넘버 분기 금지

4-7. 테스트

  • Swift Testing(@Test, #expect) — 한글 테스트명 지원: @Test("세션 시간창 밖의 미디어는 후보에서 제외된다")
  • 대상 우선순위: 시간창 매칭·업로드 재시도·오버레이 데이터 바인딩 등 Domain/Services의 순수 로직. 100% 커버리지 강박 금지
  • 유닛 테스트에서 실제 프레임워크·네트워크 호출 금지 — Services가 프로토콜이므로 mock 주입
  • 테스트를 통과시키려고 테스트를 삭제·약화 금지. 버그 수정 전 실패하는 테스트 먼저

5서버 컨벤션 Kotlin · Spring Boot

레이어드 아키텍처 + AI 선별 파이프라인. ROI 높은 규칙만 강제합니다.

5-1. 네이밍 & Kotlin 관용구

  • 패키지 전부 소문자(com.runlog.selection), 상수는 SCREAMING_SNAKE_CASE(const val MAX_UPLOAD_MB = 100)
  • val 우선, var는 재할당할 때만. 시그니처엔 불변 컬렉션(List<T>)
  • DTO/값 객체는 data class. 널 안전: !! 금지, ?.·?:·스마트 캐스트 사용
  • 레이어 접미사 강제: *Controller · *Service · *Repository · *Request/*Response(DTO) · *Entity
  • 스코프 함수는 용도대로: apply(설정) / also(부수효과) / let(변환·널가드) / run·with(블록 실행)

5-2. 패키지 / 레이어 구조

backend/src/main/kotlin/com/runlog/
com.runlog
├── config/        Spring @Configuration, 보안, S3/AWS 클라이언트 빈
├── controller/    @RestController — HTTP만. 검증(@Valid) 후 서비스 위임
├── service/       비즈니스 로직 — DTO 반환 (엔티티 반환 금지)
├── selection/     ★ AI 베스트컷 선별 파이프라인 (핵심 도메인 — 아래 5-5)
├── repository/    Spring Data 리포지토리
├── domain/        JPA 엔티티(*Entity) + 도메인 객체
├── dto/           요청/응답 DTO (data class)
├── exception/     커스텀 예외 + @RestControllerAdvice
└── mapper/        Entity ↔ DTO 매핑 (확장 함수)
  • 의존성은 아래로만: controller → service → repository. 역방향·건너뛰기 금지
  • 생성자 주입만 — 필드 @Autowired 금지. Kotlin에선 생성자 val로 자연스럽고, 불변·테스트 용이·빈 누락 즉시 실패
  • @Transactional은 서비스 메서드에. kotlin-spring(all-open)·kotlin-jpa(no-arg) 플러그인 필수
  • 설정값은 @Value 산발 대신 @ConfigurationProperties(타입 안전). AI 선별 임계값·시간창 같은 도메인 상수도 여기로

5-3. DTO vs Entity — 단단한 경계

업계 표준 규칙서비스는 DTO를 반환하고, JPA 엔티티는 절대 컨트롤러/응답으로 넘어가지 않습니다. 엔티티는 *Entity 접미사 → 컨트롤러 시그니처에 새면 즉시 눈에 띔. 지연로딩 직렬화 폭발·DB 스키마 누출·민감 필드 노출 방지.
@Entity @Table(name = "run_sessions")
class RunSessionEntity(
    @Id @GeneratedValue val id: Long = 0,
    val deviceId: String,
    val distanceMeters: Int,
    val startedAt: Instant,
)

data class RunSessionResponse(val id: Long, val distanceMeters: Int, val startedAt: Instant)

fun RunSessionEntity.toResponse() =
    RunSessionResponse(id = id, distanceMeters = distanceMeters, startedAt = startedAt)

5-4. 에러 처리 — 단일 전역 핸들러

RFC 9457 ProblemDetail(Spring Boot 3 내장) + 단일 @RestControllerAdvice. 모든 에러가 같은 형태로 나가야 iOS가 디코더 하나로 처리합니다. 실패에 200 반환 금지.

class MediaNotFoundException(id: Long) : RuntimeException("Media $id not found")

@RestControllerAdvice
class GlobalExceptionHandler : ResponseEntityExceptionHandler() {
    @ExceptionHandler(MediaNotFoundException::class)
    fun handleNotFound(ex: MediaNotFoundException): ProblemDetail =
        ProblemDetail.forStatusAndDetail(HttpStatus.NOT_FOUND, ex.message ?: "Not found").apply {
            title = "Media not found"
            setProperty("errorCode", "MEDIA_NOT_FOUND")
        }
}

5-5. AI 선별 파이프라인 규칙 핵심 도메인

  • 선별 로직과 웹 레이어 완전 분리 — selection/ 패키지는 Spring Web을 모르고, 입력(미디어 참조 목록)과 출력(CandidateScore 목록)만 가진 순수 파이프라인. 모델/라이브러리 교체·RAG 도입이 와도 이 경계는 불변
  • 재현성: 모든 CandidateScore에 modelVersion(또는 파이프라인 버전) 저장 — "왜 이 사진이 1등이었지?"에 답할 수 있어야 함. 프롬프트/임계값 변경도 버전으로 취급
  • 품질 기준(선명도·초점·노출·눈감음)의 임계값은 코드 산발 금지 — @ConfigurationProperties 한 곳
  • 선별은 비동기 작업(job) — 동기 HTTP 응답으로 처리하지 않음(미디어 수십 장 × AI 평가는 타임아웃 영역). job 패턴은 6-5
  • 외부 AI API를 쓰게 되면(예: 멀티모달 모델) 호출부는 반드시 인터페이스 뒤에 — 재시도·타임아웃·비용 로깅을 래퍼가 소유

5-6. 린트 — ktlint + detekt

  • ktlint: ktlint_official 스타일, ktlintFormat으로 자동 수정 — 스타일 논쟁 제로
  • detekt: 복잡도·긴 메서드·매직 넘버·예외 삼킴(EmptyCatchBlock 등) 탐지
  • 둘 다 버전 고정(3대 머신 드리프트 방지). 도구를 중간 도입하게 되면 baseline으로 기존 이슈 동결
  • CI 게이트: ./gradlew ktlintCheck detekt test

6API 계약 컨벤션 — iOS와 서버의 약속

상세 API 명세는 별도로 확정하더라도, 명세가 따라야 할 규칙은 지금 정합니다. 3인 팀이 실제로 가장 많이 부딪히는 지점이고, 에이전트가 양쪽 코드를 쓸 때 이 규칙이 곧 프롬프트가 됩니다.

6-1. URL · 리소스

  • 베이스: /api/v1/… — 처음부터 버전 프리픽스 (앱은 강제 업데이트가 안 되므로 서버가 구버전을 감당해야 함)
  • 리소스는 복수형 kebab-case: /api/v1/run-sessions/{id}/media-assets
  • 동사는 URL에 넣지 않음 — 행위가 필요하면 하위 리소스로: POST /run-sessions/{id}/selection-jobs

6-2. JSON 필드

  • 케이싱은 결정 ② — 권장은 camelCase(Kotlin data class·Swift Codable 기본값과 일치 → 양쪽 매핑 코드 0줄)
  • 단위를 필드명에: distanceMeters, durationSec, avgPaceSecPerKm — 단위 애매함이 버그가 되는 걸 이름이 차단
  • 날짜·시간은 ISO 8601 UTC(2026-07-02T08:00:00Z), 필드명은 ~At 접미사: startedAt, capturedAt, uploadedAt. 타임존 변환은 클라이언트 표시 계층의 책임
  • enum 값은 SCREAMING_SNAKE_CASE 문자열("PROCESSING") — 숫자 코드 금지. 서버는 모르는 enum 값이 와도 깨지지 않게, 클라이언트는 unknown 케이스 필수
  • 도메인 용어는 엔티티 표기 그대로: runSession, mediaAsset, candidateScore — iOS 코드·서버 코드·API가 한 언어

6-3. 페이지네이션 · 공통 규칙

  • 목록 응답은 처음부터 봉투로: { "items": […], "nextCursor": "…" } — 배열을 직접 반환하면 나중에 필드 추가가 불가능
  • null 필드는 생략하지 않고 null로 명시(iOS 옵셔널 디코딩 일관성) — 단수 결측 지표(GPS 없는 세션 등)는 명세에 nullable 명시

6-4. 에러 계약

  • 모든 에러는 ProblemDetail(RFC 9457) + errorCode 확장 필드: RUN_NOT_FOUND, MEDIA_TOO_LARGE, SELECTION_FAILED…
  • iOS는 errorCode로 분기하고 detail은 로깅용 — 화면 문구는 클라이언트가 소유
  • errorCode 목록은 서버 레포의 단일 enum이 정본, 변경 시 API 명세 문서와 함께 PR

6-5. 미디어 업로드 · 비동기 작업 패턴 핵심 플로우

권장 플로우 — presigned URL + job 원본이 서버 프로세스를 통과하지 않게 합니다. ① POST /media-assets(메타데이터) → 서버가 S3 presigned URL 발급 → ② 클라이언트가 S3로 직접 PUT → ③ POST /run-sessions/{id}/selection-jobs로 선별 요청 → ④ GET /selection-jobs/{id} 폴링(status: QUEUED | PROCESSING | COMPLETED | FAILED) → ⑤ 완료 시 candidateScores 수신.
  • 오래 걸리는 작업(AI 선별·영상 처리)은 전부 *-jobs 리소스 패턴 — 동기 응답에 30초짜리 작업 넣지 않기
  • 업로드는 재개 가능해야 함: 클라이언트는 실패 항목만 재시도, 서버는 phAssetId+체크섬 기준 멱등 처리(중복 업로드 무해)
  • 영상은 원본 대신 선별용 저해상 프록시 업로드를 기본으로 검토(비용·속도) — 결정 ④와 연결

6-6. 명세의 정본

  • 서버에 springdoc-openapi를 붙여 OpenAPI 스펙 자동 생성, 스냅샷(openapi.yaml)을 레포에 커밋 — API 변경이 diff로 보이고, 에이전트가 iOS 클라이언트 코드를 쓸 때 이 파일을 읽으면 됨
  • 계약 변경은 서버 PR에 스펙 diff 포함 + iOS 담당 리뷰 필수 — 3인 팀의 계약 위원회는 PR 리뷰 그 자체

7런로그 특화 규칙 — 이 프로젝트에만 있는 것들

일반 컨벤션으로 커버되지 않는, 제품이 만들어낸 우리만의 규칙 4가지. CLAUDE.md 고가치 항목입니다.

7-1. 디자인 토큰 1:1 매핑 — hex/px 하드코딩 금지

디자인 문서의 점 표기 토큰({colors.primary}, {spacing.sm}, {rounded.full})을 Swift 네임스페이스로 그대로 옮깁니다. 이름이 같아야 디자인 문서 ↔ 코드 ↔ 에이전트 대화가 한 언어가 됩니다.

enum DS {
    enum Colors {
        static let primary = Color(hex: 0xFFB300)   // {colors.primary} Chrono Amber
        static let canvas = Color(hex: 0x131313)    // {colors.canvas}
    }
    enum Spacing { static let sm: CGFloat = 16; static let md: CGFloat = 24 }
    enum Rounded { static let md: CGFloat = 12; static let full: CGFloat = 999 }
}
  • 뷰 코드에 hex 리터럴·매직 px가 보이면 반려. 단일 액센트 원칙(앰버는 주 CTA·선택·상위 3 랭크에만, 화면당 3개 이하)은 린터가 못 잡으므로 PR 리뷰 체크 항목
  • 수치 충돌 시 design.md가 정본. 기록 수치엔 {typography.metric-*}(Barlow Condensed 600 + tabular figures)만

7-2. 분석 이벤트 네이밍 — 첫날 못 박아야 하는 이유

퍼널 지표(재사용률·TT-Share·후보 채택률)가 베타의 성패 판정 기준입니다. 이벤트명을 나중에 바꾸면 지표 연속성이 끊깁니다.

  • 이벤트명 snake_case, <대상>_<동사past>: reel_template_selected(디자인 문서 기정의), bestcut_candidate_adopted, draft_exported. 파라미터 키도 snake_case
  • 문자열 리터럴 산발 금지 — 모든 이벤트는 AnalyticsEvent 카탈로그(enum) 한 곳에서만 정의. grep 한 번으로 전체 목록이 나와야 함
  • SDK 미정이므로 AnalyticsClient 프로토콜 뒤에 래핑 — SDK 결정이 코드 전체에 스며들지 않게. 오프라인 큐+배치 발송은 래퍼의 책임
  • 이벤트 발화를 눈으로 검증할 디버그 뷰를 초기부터 포함 (관측성 요구)

7-3. 릴스 템플릿 = 데이터 — 코드에 타이밍 하드코딩 금지

  • 템플릿(templateId, slotCount, 타이밍)은 Resources/ReelTemplates/*.json에만 존재. 컴포지션 엔진은 데이터를 해석할 뿐 특정 템플릿을 알지 못함 — 트렌드 대응이 "코드 수정"이 아니라 "데이터 추가"여야 함
  • templateId는 kebab-case+버전(photo-dump-v1), 타이밍은 ms 정수, 스키마 검증 테스트 1개가 모든 JSON을 순회
  • 릴스 템플릿(편집 프리셋)과 오버레이 스타일(기록 그래픽)은 별개 개념 — 이름·필드 섞지 않기

7-4. 미디어 · 개인정보 취급 레드라인 CRITICAL — CLAUDE.md 최상단

사용자의 사진·영상·건강 데이터를 서버에 올리는 서비스입니다. 신뢰가 곧 제품이고, 아래 규칙은 어떤 세션에서도 예외가 없습니다.

🚫 절대 금지
  • 미디어 업로드·저장은 베스트컷 선별 목적에 한정. 목적 외 사용(학습 데이터 축적, 제3자 전송) 코드 금지
  • 얼굴 생성·변형·보정 금지 — 인식·품질 평가만 허용 (제품 핵심 원칙)
  • 사진·영상 내용, GPS 좌표, 건강 수치 원본을 서버 로그·분석 이벤트에 남기지 않음 — 로그에는 ID·크기·상태만
  • S3 버킷 공개 설정 금지, presigned URL 만료는 짧게. AWS 키·시크릿 커밋 금지(pre-commit 검사)
  • HealthKit 데이터의 광고 목적 사용 금지 (Apple 정책 — 리젝 사유)
  • 원본 보존 기간(선별 완료 후 즉시 삭제 vs N일 보관)은 결정 ⑦ — 코드보다 먼저 정해야 하는 정책
  • 전송은 항상 HTTPS, 저장은 S3 SSE 암호화 기본. 사용자 삭제 요청 시 원본+파생물(스코어·썸네일) 일괄 삭제 가능한 구조로 설계
