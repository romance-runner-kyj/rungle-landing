TL;DR

조사 요약

가장 직접적인 벤치마크는 Relive다 — "활동 데이터를 애니메이션 3D 영상 스토리로 자동 변환"이라는, Run-log와 정확히 같은 가치 제안 구조를 판다. AI 영상 편집 앱들(Captions, OpusClip, Submagic)은 공통적으로 결과 중심 수치 헤드라인 + 제품 즉시 체험형 진입점 + 대형 소셜 프루프 패턴을 쓰고, Runna는 소셜 프루프 상단 집중 + 리스크 제거 CTA 문구의 교과서다.

핵심 결론

검증된 6개 레퍼런스는 전부 출시 후 제품이라 이메일 수집이 없거나 보조적이다(다운로드/가입 직행). 따라서 Run-log v3는 출시 후 제품의 패턴(카피 톤·소셜 프루프·섹션 흐름·즉시 체험 감각)을 차용하되, 전환 장치만 waitlist 이메일 폼(Formspree mlgkkrrv)으로 치환하는 접근이 현재 근거상 가장 안전하다. 추천 조합: Relive식 감성 섹션 흐름 + Submagic식 결과 카피("기록에서 릴스까지, 자동으로") + 단일 이메일 필드 waitlist 폼.

Run-log v3 Application

v3 적용 제안 5가지

검증 통과한 18개 주장에서 도출한 조합 제안. 각 요소의 원본 패턴은 전부 HIGH 확신도. (waitlist 번안 효과 자체는 검증 사례가 없어 종합 확신도 MEDIUM)

  1. 히어로 — Submagic 카피 공식 × Relive 비주얼

    결과 중심 카피("러닝 기록에서 릴스까지, 자동으로" — PRD가 허용하면 수치 결합) + 러닝 라이프스타일 실사 배경 + 완성 릴스가 재생되는 폰 목업. Relive처럼 서브카피를 최소화하고 CTA로 직행.

  2. CTA — 단일 이메일 필드 waitlist 폼 (히어로 배치 + 4회 이상 반복)

    Formspree mlgkkrrv 폼을 히어로에 배치. Runna식 리스크 제거 마이크로카피("출시 시 우선 초대" 등, PRD 기준으로 확정) + OpusClip식 부담 제거 문구 병기. Videoleap/Submagic처럼 페이지 전반 4회 이상 반복(히어로 / 사용법 직후 / 감성 섹션 / 최하단).

  3. 섹션 흐름 — Relive 감성 뼈대 + Submagic 3단계 삽입

    히어로 + waitlist 폼핵심 가치 "당신의 러닝 스토리"소셜 프루프(정성적)기능 3카드3단계: 기록 연동 → AI 편집 → 릴스 공유트래커 호환 (Strava/Garmin/애플워치 — PRD 확인 필요)감성 섹션최종 CTA + 폼

  4. 소셜 프루프 — 출시 전 대체재 (진실성 가드 준수)

    평점·사용자 수가 없으므로: 베타 테스터 후기(실존하는 것만), 생성된 릴스 샘플 갤러리(Captions 스타일 썸네일 그리드 차용)를 상단 배치. ⚠ 가상 대기자 수 카운터는 진실성 가드 위반 — 실제 수치가 아니면 금지.

  5. 즉시 체험 감각 — 데모 영상/갤러리로 번안

    Captions/OpusClip의 인터랙티브 진입점을 출시 전 버전으로: 히어로 또는 직하단에 실제 생성 릴스 데모 자동재생 또는 템플릿 스타일 갤러리 노출. 실제로 만들 수 있는 결과물만 노출(존재하지 않는 기능 주장 금지).
Caveats & Refuted Claims

조사의 한계 · 기각된 주장

  • waitlist 카테고리 공백 — 조사 목표 (3)의 우수 사례는 검증 확보 실패. 관련 제안은 출시 후 패턴의 번안이며 검증된 사례 기반이 아님.
  • Strava, Nike Run Club, CapCut 미검증 — 원 조사 범위였으나 검증 통과 주장이 없어 미포함. 필요 시 재조사.
  • 비주얼 디테일(컬러·타이포·모션) 미확보 — HTML 텍스트 기반 검증의 한계로 카피·구조·CTA 중심으로 정리됨. 시각 분석은 스크린샷 기반 별도 조사 필요. 단, 디자인은 어차피 docs/design.html(크로노 앰버 다크 시스템)이 SSOT.
  • 시점 민감성 — 전부 2026-07-02 라이브 기준. 이들 사이트는 A/B 테스트가 잦아 문구·수치가 수시로 변함.
  • 미세 불일치 — Runna 평점 블록은 로케일별 변형 수치 가능. OpusClip 소셜 프루프는 히어로 '직하단'이 아니라 지표 3개 이후 위치.

v3 개발 브리프 원문

아래는 사용자가 작성한 v3 리빌드 브리프 전문이다. 다음 세션의 개발 지침으로 그대로 적용한다.

배경

러닝 기록 자동 릴스/영상 편집 앱 Run-log의 랜딩페이지를 처음부터 새로 만든다. 기존 v2는 runlog-landing-page.vercel.app (ko) · /en (en)에 라이브 중이지만, 브랜드 컬러·로고가 새로 확정되었고 PRD가 대대적으로 수정되어 기존 코드는 계승하지 않고 싹 갈아엎는다. 이 폴더(~/Documents/randing/runlogv2)가 새 프로젝트 루트. 기존 레포(~/Documents/runlog-landing-page)는 참고용.

입력 자료 (구현 전 전부 정독 — SSOT)

  • PRD: docs/run-log-prd-v2-overview.html — 서비스 정의·기능 범위의 유일한 기준
  • 디자인 시스템: docs/design.html — 크로노 앰버(#FFB300) 다크 시스템, Pretendard + Barlow Condensed
  • 코드 컨벤션: docs/런로그-코드컨벤션-가이드-v3.html
  • 레퍼런스: 본 문서의 조사 결과 (레퍼런스 섹션 + v3 제안)
  • 로고: 별도 파일 없음 — docs/design.html의 brand-pill 기하 스펙(400m 트랙 필 앰버 2px 외곽선 + 트랙 위 앰버 도트)이 로고 원본. CSS/SVG로 재현하며 파비콘·OG 이미지도 이 스펙에서 파생 생성.

⚠ PRD/디자인 md와 아래 "계승 사항"이 충돌하면 새 PRD/디자인이 우선. 단, 충돌 지점은 사용자에게 보고할 것.

기존 v2에서 계승할 것 (운영 자산)

  • 이메일 수집: Formspree form ID mlgkkrrv 그대로 사용 (허니팟 + ARIA 처리 포함)
  • 다국어 구조: ko=/(기본), en=/en. Next.js route-group 2-root-layout 방식 — 각 루트가 자기 <html lang>을 SSR, 카피는 서버에서 dict 주입(localStorage 없음, FOUC 0). 언어 토글은 Link로 해시 보존. v2에서 검증된 구조라 재사용 권장.
  • SEO: hreflang·canonical·sitemap·robots 세트 유지. SITE_URL은 env NEXT_PUBLIC_SITE_URL로 override 가능하게.
  • 카피 SSOT 패턴: app/lib/copy.ts 하나에 ko/en 동형 타입 강제.

진실성 가드 (새 PRD가 달리 말하지 않는 한 유지)

  • 출시 전 제품 — 존재하지 않는 기능을 주장하지 않는다.
  • 가상 대기자 수 같은 허위 소셜프루프 금지 — 정성적 표현만.

v2 기술 교훈 (같은 함정 피하기)

  • Tailwind v4에서 py-[--space-section-y] 같은 CSS 변수 arbitrary value 무효 → 명시적 유틸(py-28 md:py-36) 사용.
  • 디자인 토큰은 globals.css의 @theme에 정의.
  • next/font/google은 빌드 타임 다운로드라 오프라인 CI에서 깨질 수 있음 → 폰트 self-host(public/fonts/) 우선 고려.
  • OG 이미지는 ko/en 각각 생성, 인스타/카톡 미리보기까지 검증.

스택 & 검증

  • Next.js (App Router) + React + Tailwind v4 + TypeScript, 패키지 매니저 pnpm.
  • 완료 기준: pnpm build && pnpm lint 통과 + Playwright/헤드리스 브라우저로 ko/en 양쪽 실제 렌더 확인.

배포

  • Vercel CLI 직배포: npx vercel --prod --yes (계정 sunishae44-6783 인증됨).
  • ⚠ 기존 프로젝트 runlog-landing-page에 덮어쓸지 / 새 Vercel 프로젝트로 갈지 — 미확정, 사용자에게 확인할 것.

진행 방식

  • ① 입력 자료를 전부 읽고, 이해한 서비스 정의·페이지 구조(섹션 구성)·디자인 방향을 요약해서 먼저 사용자에게 확인받는다.
  • ② 승인 후 섹션 단위로 구현. 카피는 ko 먼저 확정 → en 번역.
  • ③ PRD에 없는 내용을 지어내지 말고, 애매하면 물어볼 것.

다음 세션 시작 가이드

  1. 정독

    docs/run-log-prd-v2-overview.html → docs/design.html → docs/런로그-코드컨벤션-가이드-v3.html → 본 문서 순으로 읽는다.

  2. 사용자 확인 (착수 전)

    ① Vercel 배포 대상(기존 프로젝트 덮어쓰기 vs 신규) ② 이해한 서비스 정의·섹션 구성·디자인 방향 요약 승인 ③ 폰 목업에 넣을 실제 앱 화면/릴스 데모 영상 유무(없으면 CSS 시뮬레이션으로 진행) — 이 3가지를 확인받고 시작한다.

  3. 스캐폴딩

    pnpm + Next.js(App Router) + Tailwind v4 + TS. route-group 2-root-layout(ko/en), app/lib/copy.ts SSOT, 폰트 self-host.

  4. 섹션 단위 구현

    본 문서 "v3 적용 제안"의 섹션 흐름을 기본안으로, PRD와 충돌 시 PRD 우선(충돌 보고). 카피 ko 확정 → en 번역.

  5. 모션 로고 제작 (병행 작업 — 사용자 요청)

    brand-pill 도트가 현재 정적 위치(오른쪽 위, 인스타 점 위치)에서 출발해 트랙을 정확히 한 바퀴 돌고 제자리에 멈추는 애니메이션. 산출물 3종: ① 웹용 CSS/SVG 애니메이션(랜딩 히어로·로딩 재사용) ② 투명 배경 영상(ProRes 4444 또는 HEVC 알파 — 인스타 릴스 편집 오버레이용) ③ 다크 배경 MP4(인트로/아웃트로 범퍼용). 제작 방법: 헤드리스 브라우저 프레임 캡처 → ffmpeg 인코딩. 앰버 글로우(box-shadow rgba(255,179,0,.5)) 유지, Reduce Motion 대응은 웹 버전에만 적용.

  6. 검증 & 배포

    pnpm build && pnpm lint + ko/en 실렌더 확인 + OG 이미지(ko/en) 검증 → 사용자 승인 후 Vercel 배포.
